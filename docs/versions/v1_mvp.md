# Cluster v1: MVP

## Purpose

기존 Cluster MVP의 구현 범위, 성과, 한계를 기록한다. v1은 실패한 버전이 아니라, 기능 구현과 아이디어 검증에 초점을 둔 첫 번째 버전이다.

## Version Summary

Cluster v1은 사람, 장소, 일정, 사진 업로드, 얼굴 인식 서버를 연결해 사용자의 만남 기록을 자동으로 정리하려는 MVP였다.

v1의 핵심 성과는 다음과 같다.

- 사람/장소/일정/활동 로그 도메인 구현
- 사진 EXIF 기반 날짜/위치 분석 구현
- 얼굴 인식 서버 연동 구현
- 사진 업로드 결과를 일정/장소/사람 후보와 연결하는 흐름 구현
- 개인 프로젝트 구현 이후 교수님의 제안으로 학회 발표/논문으로 확장
- 학회 발표/논문 및 수상을 통해 아이디어의 가능성 검증

## v1 Limitation Categories

### 1. Matching Quality

#### L-01. 같은 장소 판정이 임의 threshold에 의존한다.

v1은 사진 위치와 등록 장소가 같은 장소인지 판단할 때 공간/시간 범위를 하드코딩된 값으로 사용한다.

문제점:

- 왜 해당 거리 기준을 사용하는지 평가 근거가 부족하다.
- 장소 밀집 지역에서는 오탐 가능성이 높다.
- 장소가 넓거나 사용자의 이동 패턴이 다른 경우 같은 기준을 적용하기 어렵다.
- adaptive threshold나 context-aware scoring이 없다.

#### L-02. 같은 일정 판정이 장소 판정 결과에 과하게 의존한다.

일정 매칭은 날짜와 장소 매칭 결과에 강하게 의존한다.

문제점:

- 장소 판정이 틀리면 일정 판정도 함께 틀어질 수 있다.
- 일정 제목, 참여 인물, 시간대, 과거 패턴 같은 추가 context를 충분히 활용하지 못한다.
- 일정 후보 간 ranking이나 confidence가 없다.

#### L-03. 사람 인식 성능을 측정할 수 없다.

v1은 얼굴 인식 결과를 사용하지만, 인식률과 다중 인물 인식률을 평가하는 지표가 부족하다.

문제점:

- 얼굴 인식 정확도 지표가 없다.
- 여러 사람이 있는 사진에서의 매칭 품질을 측정하기 어렵다.
- unknown face 판정 성능을 측정하기 어렵다.
- benchmark dataset과 regression test가 없다.

### 2. Architecture

#### L-04. 사진 업로드와 수동 일정 확정의 내부 분기가 복잡하다.

v1은 사진 업로드, 일정 생성, 일정 확정, ActivityLog 생성이 여러 케이스로 나뉘어 처리된다.

문제점:

- 분석 단계와 확정 단계의 책임 경계가 불분명하다.
- 케이스별 예외 처리 기준이 명확히 문서화되어 있지 않다.
- 플로우가 늘어날수록 service 로직이 복잡해진다.
- 어떤 시점에 DB 변경이 발생해야 하는지 판단하기 어렵다.

#### L-05. 데이터 일관성 기준이 약하다.

ActivityLog, Schedule, Person count, Place visit_count가 연결되어 있지만 갱신 기준과 트랜잭션 경계가 명확하지 않다.

문제점:

- ActivityLog 중복 생성 방지 기준이 약하다.
- Schedule 완료 처리와 ActivityLog 생성의 관계가 명확하지 않다.
- Person/Place count 갱신이 실제 활동 기록과 항상 일치한다는 보장이 약하다.
- 부분 실패 시 rollback 기준이 명확하지 않다.

#### L-06. 외부 의존성이 service 로직에 섞여 있다.

AI 서버, Cloudinary, Kakao API 같은 외부 호출이 명확한 client/adapter 경계로 분리되지 않았다.

문제점:

- 외부 API 실패를 테스트하기 어렵다.
- mock 테스트가 어렵다.
- latency와 fallback 정책을 일관되게 관리하기 어렵다.
- provider 교체 비용이 크다.

### 3. Reliability and Observability

#### L-07. 얼굴 임베딩 API latency가 크고 통제하기 어렵다.

v1은 HuggingFace 기반 AI 서버/API 호출에 의존하며, 호출 시간이 길고 불안정할 수 있다.

문제점:

- cold start와 모델 로딩 비용이 크다.
- 네트워크 지연을 통제하기 어렵다.
- 요청 timeout과 fallback 정책이 명확하지 않다.
- 얼굴 인식 단계가 전체 사진 분석 UX를 지연시킬 수 있다.

#### L-08. 시스템 단위 로그/분석 체계가 부족하다.

사진 분석 파이프라인의 각 단계가 얼마나 걸리고 어디서 실패하는지 추적하기 어렵다.

문제점:

- 단계별 latency를 확인하기 어렵다.
- 외부 API 실패율을 확인하기 어렵다.
- fallback 발생률을 확인하기 어렵다.
- 실제 로그 기반 개선 루프를 만들기 어렵다.

#### L-09. 비용/latency trade-off 판단 기준이 없다.

AI 호출을 늘렸을 때 정확도는 개선될 수 있지만 비용과 latency가 증가한다.

문제점:

- rule-based 방식과 AI-assisted 방식의 비교 기준이 없다.
- 어떤 상황에서 AI 호출이 필요한지 판단 기준이 없다.
- 정확도, 비용, 속도 사이의 trade-off를 설명하기 어렵다.

### 4. Security and Product UX

#### L-10. 사진과 개인정보 보호 설계가 약하다.

Cluster는 사진, 얼굴 임베딩, 위치, 관계 데이터를 다루므로 민감도가 높다.

문제점:

- 사진 저장/전송/삭제 정책이 명확하지 않다.
- 얼굴 임베딩의 보호 정책이 명확하지 않다.
- 위치 데이터와 활동 로그의 민감도에 대한 기준이 부족하다.
- 로그에 민감 데이터가 남을 위험이 있다.

#### L-11. 사용자 입력 부담이 크다.

v1은 사람, 장소, 일정을 사용자가 직접 입력해야 하는 비중이 크다.

문제점:

- 초기 사용 진입 장벽이 높다.
- 연락처/캘린더 import 후보 구조가 없다.
- 실제 서비스 사용성 관점에서 장기 사용을 유도하기 어렵다.

### 5. Documentation and Testing

#### L-12. API 계약과 설계 문서가 부족하다.

v1은 기능 구현은 되어 있지만, 요구사항, 기능 명세, API, 데이터 스키마, 시스템 흐름이 포트폴리오 문서로 정리되어 있지 않다.

문제점:

- 면접관이 설계 의도를 빠르게 이해하기 어렵다.
- 코드 변경 시 문서와 구현이 함께 관리되지 않는다.
- API 요청/응답, 에러 형식, 핵심 시퀀스가 명확하지 않다.

#### L-13. 테스트 전략이 부족하다.

v1은 핵심 도메인 로직과 외부 API 연동을 안정적으로 검증하는 테스트가 부족하다.

문제점:

- 사진 그룹화 테스트가 부족하다.
- 일정/장소/사람 매칭 테스트가 부족하다.
- AI 서버 mock 테스트가 부족하다.
- legacy vs v2 비교 테스트가 없다.

## v1 Conclusion

v1은 아이디어를 실제 동작하는 제품으로 구현하고, 학회 발표/논문 및 수상을 통해 가능성을 인정받은 버전이다. 그러나 포트폴리오에서 백엔드 설계 능력과 AI application engineering 역량을 보여주기에는 architecture, evaluation, observability, security, testing 측면의 한계가 명확하다.

v2는 v1의 제품 문제를 유지하되, 위 한계를 기준으로 백엔드 구조와 AI 파이프라인을 재설계한다.
