# 01. Requirements

## Purpose

Cluster가 해결해야 하는 문제와 요구사항을 정의한다. 이 문서는 구현 방법보다 "무엇이 왜 필요한가"를 먼저 정리한다.

## Problem Definition

사용자는 사람들과의 만남을 사진, 일정, 지도, 연락처에 흩어진 형태로 남긴다. 하지만 이 데이터들은 서로 연결되어 있지 않기 때문에 시간이 지나면 특정 관계의 흐름이나 장소 방문 기록을 다시 파악하기 어렵다.

Cluster는 사용자가 가진 사진과 일정 데이터를 기반으로 만남 기록을 자동 분석하고, 사람/장소/일정/활동 로그로 연결된 구조화 데이터를 만든다.

## User Requirements

### UR-01. 사용자는 자신의 관계 대상을 등록하고 관리할 수 있어야 한다.

필요성: 만남 기록을 사람 중심으로 다시 확인하려면, 기록의 대상이 되는 사람 정보가 필요하다.

- 사용자는 사람의 이름, 관계, 연락처, 주소, 프로필 사진을 등록할 수 있다.
- 등록된 사람은 이후 일정, 사진 분석 결과, 활동 로그와 연결된다.
- 사람별 만남 횟수와 상태를 확인할 수 있어야 한다.

### UR-02. 사용자는 자주 방문하거나 만남이 발생한 장소를 등록하고 관리할 수 있어야 한다.

필요성: 사진의 위치 정보와 일정 장소를 비교하려면 기준이 되는 장소 데이터가 필요하다.

- 사용자는 장소를 검색하거나 선택해 등록할 수 있다.
- 장소는 좌표, 이름, 카테고리 정보를 가진다.
- 장소별 방문 횟수와 함께 방문한 사람 목록을 확인할 수 있어야 한다.

### UR-03. 사용자는 예정된 만남을 일정으로 등록할 수 있어야 한다.

필요성: 사진 업로드 시 기존 일정과 자동 매칭하려면 사전에 계획된 일정 데이터가 필요하다.

- 사용자는 제목, 날짜, 시간, 장소, 참여 인물, 메모를 포함한 일정을 등록할 수 있다.
- 일정은 예정 상태와 완료 상태를 가질 수 있다.
- 완료된 일정은 실제 활동 로그와 연결될 수 있어야 한다.

### UR-04. 사용자는 사진을 업로드해 만남 기록 후보를 자동 분석할 수 있어야 한다.

필요성: 사용자가 일일이 언제, 어디서, 누구와 만났는지 입력하지 않아도 사진 기반으로 후보를 만들 수 있어야 한다.

- 사용자는 여러 장의 사진을 업로드할 수 있다.
- 시스템은 사진의 EXIF 날짜/위치 정보를 추출한다.
- 시스템은 날짜와 위치 기준으로 사진을 그룹화한다.
- 시스템은 기존 일정, 장소, 등록 인물과 비교해 후보 결과를 반환한다.

### UR-05. 사용자는 분석 결과를 확인한 뒤 실제 활동 기록으로 확정할 수 있어야 한다.

필요성: AI/EXIF 분석 결과는 추론 결과이므로, DB에 실제 기록으로 저장하기 전에 사용자 확인이 필요하다.

- 분석 단계에서는 DB에 활동 기록을 확정 저장하지 않는다.
- 사용자가 확정하면 ActivityLog가 생성된다.
- 확정된 기록은 사람, 장소, 일정, 사진과 연결된다.

### UR-06. 사용자는 사람, 장소, 캘린더 화면에서 확정된 기록을 다시 확인할 수 있어야 한다.

필요성: 기록의 가치는 저장보다 재조회와 연결성에서 나온다.

- 사람 상세에서 해당 사람과의 만남 기록을 확인할 수 있다.
- 장소 상세에서 해당 장소의 방문 기록과 함께 방문한 사람을 확인할 수 있다.
- 캘린더에서 일정과 완료된 기록을 확인할 수 있다.


### UR-07. 사용자는 개인 계정과 프로필을 통해 자신의 데이터 공간을 가질 수 있어야 한다.

필요성: 사람, 장소, 일정, 사진 기록은 개인 단위로 분리되어야 하며, 로컬 데모에서도 사용자별 데이터 소유 구조가 명확해야 한다.

- 사용자는 회원가입과 로그인을 할 수 있다.
- 사용자는 본인 프로필과 기본 정보를 관리할 수 있다.
- 사용자의 데이터는 다른 사용자 데이터와 분리되어야 한다.

### UR-08. 사용자는 연락처와 캘린더 데이터를 선택적으로 가져올 수 있어야 한다.

필요성: 사람과 일정을 모두 수동 입력하게 하면 사용 부담이 크다. 외부 데이터 연동은 초기 입력 비용을 줄이는 핵심 사용성 개선이다.

- 사용자는 연동 없이 수동 입력으로 시작할 수 있다.
- 사용자는 연락처 기반 사람 후보를 가져올 수 있다.
- 사용자는 캘린더 기반 일정 후보를 가져올 수 있다.
- 가져온 데이터는 즉시 확정 저장하지 않고 import candidate로 보여준다.
- 사용자가 선택/수정/확정한 데이터만 Cluster의 Person 또는 Schedule로 저장한다.

### UR-09. 사용자는 분석 결과가 왜 추천되었는지 이해할 수 있어야 한다.

필요성: 사진 분석과 AI 매칭 결과는 추론이므로 사용자가 결과를 신뢰하고 수정할 수 있는 근거가 필요하다.

- 시스템은 일정/장소/인물 후보를 confidence와 함께 제공할 수 있다.
- 시스템은 주요 판단 근거를 사용자에게 설명할 수 있다.
- 사용자는 추천 결과를 그대로 확정하거나 수정할 수 있다.

## Backend Requirements

### BR-01. 백엔드는 도메인 모델 간 관계를 명확히 관리해야 한다.

- User는 Person, Place, Schedule, ActivityLog를 소유한다.
- Schedule은 여러 Person과 연결될 수 있다.
- ActivityLog는 실제 발생한 만남 기록이며 Person, Place, Photo와 연결된다.
- Photo는 분석 결과가 아니라 확정된 ActivityLog에 귀속된다.

### BR-02. 사진 분석과 활동 기록 확정은 분리되어야 한다.

- 사진 분석 API는 후보 결과를 반환한다.
- 활동 기록 확정 API는 DB 변경을 수행한다.
- 이 분리는 잘못된 자동 저장과 중복 기록 생성을 줄이기 위해 필요하다.

### BR-03. 백엔드는 사진 분석 파이프라인을 단계별로 분리해야 한다.

- 파일 검증
- EXIF 추출
- 사진 그룹화
- 장소 후보 탐색
- 일정 후보 매칭
- AI 서버 얼굴 인식 요청
- 결과 병합
- 사용자 확인용 응답 생성

### BR-04. 백엔드는 데이터 일관성을 보장해야 한다.

- ActivityLog 확정 시 중복 기록 생성을 방지한다.
- 사람의 만남 횟수는 실제 활동 로그 기준으로 갱신한다.
- 장소 방문 횟수는 실제 활동 로그 기준으로 갱신한다.
- Schedule 상태는 ActivityLog 확정 여부와 일관되게 관리한다.

### BR-05. 백엔드는 외부 의존성을 명확한 client 경계로 다뤄야 한다.

- AI 서버 호출은 AI client로 분리한다.
- Cloudinary 호출은 storage client로 분리한다.
- Kakao 장소 검색은 place search client로 분리한다.
- 외부 서비스 실패가 전체 시스템 실패로 바로 이어지지 않도록 정책을 둔다.


### BR-06. 백엔드는 AI 매칭 오케스트레이션 계층을 가져야 한다.

- deterministic rule은 후보군을 좁히는 역할을 담당한다.
- AI orchestration은 후보 ranking, confidence, reason 생성을 담당한다.
- AI 판단 결과는 사용자 확정 전까지 DB 변경을 일으키지 않는다.
- AI orchestration은 나중에 LLM, rule engine, heuristic scorer를 교체할 수 있는 구조여야 한다.

### BR-07. 백엔드는 외부 데이터 import를 adapter 구조로 다뤄야 한다.

- 연락처, 캘린더, 카카오 같은 외부 데이터 소스는 adapter 경계로 분리한다.
- import 결과는 Person 또는 Schedule이 아니라 ImportCandidate로 먼저 다룬다.
- 사용자가 확정한 candidate만 실제 도메인 데이터로 저장한다.
- 포트폴리오 v2에서는 실제 연동보다 mock/seed 기반 adapter와 확장 가능한 구조를 우선한다.

## AI Integration Requirements

### AIR-01. AI 서버는 메인 백엔드와 분리되어야 한다.

필요성: 얼굴 인식 모델은 무거운 의존성과 모델 로딩 비용이 있으므로 메인 API 서버와 분리하는 것이 적절하다.

- AI 서버는 얼굴 임베딩 추출 API를 제공한다.
- AI 서버는 사진 내 얼굴 감지와 등록 인물 매칭 API를 제공한다.
- 메인 백엔드는 HTTP 기반으로 AI 서버를 호출한다.

### AIR-02. AI 서버 실패 시 fallback 정책이 있어야 한다.

- AI 서버 호출이 실패해도 EXIF 기반 분석 결과는 반환할 수 있어야 한다.
- 얼굴 매칭 결과는 빈 결과로 대체할 수 있어야 한다.
- 사용자는 AI 매칭 실패 상황을 이해할 수 있어야 한다.

### AIR-03. AI 연동은 테스트 가능해야 한다.

- 실제 AI 서버 호출 없이 mock client로 사진 분석 파이프라인을 테스트할 수 있어야 한다.
- AI 서버 응답 스키마는 명확히 정의되어야 한다.


### AIR-04. 얼굴 인식 기능은 교체 가능한 provider 구조로 설계되어야 한다.

- 메인 백엔드는 특정 얼굴 인식 라이브러리에 직접 의존하지 않는다.
- 얼굴 임베딩 추출, 유사도 계산, threshold 판단은 명확한 provider/client 경계로 분리한다.
- 기존 DeepFace 기반 구현은 legacy provider로 격리할 수 있어야 한다.
- 향후 더 나은 pretrained embedding model, 온디바이스 모델, mock provider로 교체 가능해야 한다.

## Non-Functional Requirements

### NFR-01. 로컬 데모가 쉬워야 한다.

- 면접 환경에서 빠르게 실행할 수 있어야 한다.
- seed data 또는 demo scenario로 핵심 플로우를 재현할 수 있어야 한다.

### NFR-02. API 문서와 실제 동작이 일치해야 한다.

- Swagger 또는 문서화된 API 명세를 통해 주요 API를 확인할 수 있어야 한다.
- 요청/응답 예시가 실제 구현과 어긋나지 않아야 한다.

### NFR-03. 핵심 로직은 테스트 가능해야 한다.

- 사진 그룹화, 일정 매칭, 상태 갱신 같은 도메인 규칙은 단위 테스트 가능해야 한다.
- 외부 API 호출은 mock 가능해야 한다.

### NFR-04. 문서와 코드 구조가 함께 관리되어야 한다.

- API 변경 시 API 명세를 갱신한다.
- DB 모델 변경 시 데이터 스키마 문서를 갱신한다.
- 큰 설계 판단은 architecture decision 문서에 남긴다.

## Non-Goals

- 실제 사용자 유치 또는 상용 서비스 운영은 목표가 아니다.
- 대규모 트래픽 처리, 멀티 리전 배포, 고가용성 인프라는 목표가 아니다.
- 프론트엔드 디자인 고도화는 핵심 목표가 아니다.
- 얼굴 인식 모델 자체를 학습하거나 성능 개선하는 것은 목표가 아니다.
- 모바일 네이티브 앱 출시는 목표가 아니다.
- 실제 연락처/캘린더/카카오 연동의 완전한 운영 구현은 포트폴리오 v2 필수 범위가 아니다. v2에서는 adapter 구조와 데모 가능한 import 흐름을 우선한다.
